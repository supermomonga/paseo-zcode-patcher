# 公式hostからリセット権の残数と期限を読み取る

## Context and Problem Statement

ZCode公式画面はCoding Planのストックされたリセット権と有効期限を表示するが、`getEntitlementSnapshot`にはこの情報が含まれない。公式hostは別の読み取りAPI `getCodingPlanResetStatus`を提供する。利用者はPaseoでも回数と期限を確認することを希望している。

## Decision Drivers

* 資格情報と認証通信を公式hostに保持すること
* リセット権の確認と消費を区別すること
* 期限切れや取得失敗を残数として誤表示しないこと

## Considered Options

* 既存usage-stats bridgeに公式のリセット状態読み取りを追加する
* リセット回数を表示せず公式アプリでの確認に限定する

## Decision Outcome

採用: **既存usage-stats bridgeに公式のリセット状態読み取りを追加する**。

ADR 0013の許可メソッドを`getEntitlementSnapshot`と`getCodingPlanResetStatus`へ拡張する。後者には現在のCoding Plan接続先を`preferredProviderId`として渡す。公式host自身が接続先の厳密指定と資格情報取得を行う。リセットの消費・権利の請求・履歴既読化のメソッドは公開しない。

返された5時間枠・週間枠の配列から期限切れを除外し、枠ごとの回数と最も近い期限を既存カードの詳細行へ表示する。期限はUTCのISO日時と`valueFormat: "datetime"`でクライアントへ渡し、表示端末のローカル時刻へ変換する。表示形式は`2026-10-02 00:59 +09:00`とし、対象日時の夏時間も反映する。状態取得だけ失敗した場合は通常クオータを維持し、リセット残数の取得失敗を明示する。Start PlanやAPI接続先へCoding Plan専用の読み取りを送らない。セッション・接続先別の5分キャッシュは継続する。

### Consequences

* Good, because 公式hostを通して契約ごとの残数を確認でき、認証処理を複製しない。
* Good, because 読み取りだけを追加し、リセット権を消費する経路を作らない。
* Bad, because 公式の非公開APIへの依存が増え、ZCode更新時に再調査が必要になる。

### Confirmation

期限切れ・複数期限・残数ゼロ・不正応答と取得失敗の分離を対象testで確認する。実機hostの応答と表示内容を照合し、生成アプリで確認する。クオータの並び順と月間ツール残量の非表示も対象testで固定する。

## More Information

公式hostの`resolveCodingPlanResetAuthorization`、`getCodingPlanResetStatus`、公式rendererの`vWe`が根拠である。対応ZCode版の変更、Team Plan対応、リセット操作を追加する場合は境界を再検討する。
